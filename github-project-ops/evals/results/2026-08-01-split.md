# 2026-08-01 分割後の予備評価

対象は、Projects固有責務へ縮小した第4段階コミット直前の`github-project-ops`である。Issue側の作業権コメントを前提にせず、Assignee、linked branch、open PRの整合を確認済みの着手情報だけを`Status`へ同期し、実行環境が提示した追跡値だけを`Agent Run`へ記録する設計で評価した。

## 判定範囲

- 発火用の問い合わせは`github-issue-pr-ops`と同じ文面・順序にした。
- `description`の独立分類と、実際の自動読み込み率を分けた。
- 出力は、前の回答と合格条件を見ていない実行担当へ対象スキルと問い合わせだけを渡した。
- 自動読み込み率は実行環境の制約で未測定であり、自動発火の合格や全評価の収束は主張しない。

## 発火境界

学習用20問と検証用8問を3回判定した最終調整前の結果は83 / 84件だった。唯一の差異は、Issue標準メタデータの競合解消とProject同期を同時に求める問を、1実行が`both`ではなく`project`としたことだった。

Issue側の説明文を一般化して直した後、対象問、担当者変更だけの除外問、Project同期だけの問を3回ずつ判定した。結果は`both`、`none`、`project`で9 / 9件一致し、新しい曖昧点は0件だった。単発の`gh project item-list`案内を両スキルとも選ばない境界も維持した。

実際に`SKILL.md`が自動で読まれた回数は測定できていない。この結果は独立した説明文分類である。

## 修正台帳

- **Issue**: 容量が存在しない場合と、権限不足で読めない場合が区別されなかった。
  - **Cause**: どちらにも安全側の初期値を使えるように読めた。
  - **General Fix Rule**: 不在を確認できた場合だけ初期値を使い、読取不能なら書き込み前に停止する。
- **Issue**: 変更計画が「取得」「更新」という抽象表現だけになった。
  - **Cause**: 道具の選択が参照資料へ分散していた。
  - **General Fix Rule**: GitHub MCP、`gh project`、`gh api`、`jq -e`の経路を段階ごとに明記する。
- **Issue**: 停止報告にIssue/PR側資産の保全と再開地点が不足した。
  - **Cause**: 停止条件と解除後の流れが別の節にあった。
  - **General Fix Rule**: 停止理由、非変更対象、正本、解消後に探索からやり直す条件を1つの報告へまとめる。
- **Issue**: `Agent Run`同期が作業権コメントの勝者に依存し、コメント廃止後は値の由来が未定義になった。
  - **Cause**: Issue/PR側とProject側の境界を実行イベントで結んでいた。
  - **General Fix Rule**: Assignee、linked branch、open PRが一意に同じ着手を示す場合だけ`Status`へ派生同期する。`Agent Run`は現在の実行環境が提示した追跡値だけを任意記録し、未提示なら空欄、複数候補や既存値との衝突ではProject側が選ばず停止する。

## 取得できなかった値

実行時間、道具使用回数、トークン数、自動読み込み率は取得不可だった。推測値では補っていない。分割前の評価は履歴として残すが、現行スキルの合否には使わない。
