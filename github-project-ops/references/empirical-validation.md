# 経験的検証

このスキルを大きく変更した後に、発火条件と出力品質を分けて検証する。執筆者の自己確認や静的分類だけで合格にしない。

## 評価資産

- `evals/trigger-train.json`: 説明文を調整するための学習用20問。
- `evals/trigger-validation.json`: 説明文を固定した後に使う検証用8問。
- `evals/evals.json`: Project固有の成果物を評価する3シナリオと、事前に固定した合格条件。

発火用の問い合わせ集合は `github-issue-pr-ops` と同じにする。期待値だけをスキルごとに変え、次の4区分を学習用では各5問、検証用では各2問含める。

| 区分         | このスキル | `github-issue-pr-ops` |
| ------------ | ---------- | --------------------- |
| Issue/PRのみ | 発火しない | 発火する              |
| Projectのみ  | 発火する   | 発火しない            |
| 両方         | 発火する   | 発火する              |
| どちらも不要 | 発火しない | 発火しない            |

学習用の失敗だけを説明文の修正に使う。検証用の結果を見てから個別語句を足さない。

## 発火条件の検証

1. 学習用20問を、期待値を渡さず各3回実行する。
2. 各回で新しい実行担当を使い、`SKILL.md` が実際に読まれたかを記録する。
3. `should_trigger: true` は発火率50%以上、`false` は50%未満を合格とする。
4. 誤りを区分単位で一般化し、`description` の対象業務または除外業務を一度に一テーマだけ直す。
5. 学習用が安定したら説明文を固定し、未使用の検証用8問を各3回実行する。
6. 検証用で精度が落ちた場合は、問い合わせ固有の語句を足さず、Project固有業務と近接業務の境界を書き直す。

特に、Projectの利用が確認できない次の依頼では発火させない。

- Issue分割、Issue本文、Milestone、Issue Forms、`Assignee`、linked branch、PR本文、マージ規約だけの設計。
- IssueやPRの閲覧、要約、担当者変更、翻訳。
- 通常のコードレビュー、レビュー指摘対応、CI失敗修正。
- 一般的なGit操作や単発の`gh`コマンド。
- WBS、見積り、複数エージェント、ロードマップという語だけがあり、GitHub Projectsの利用が確認できない依頼。

## 出力品質の検証

1. `evals/evals.json` の合格条件を変更前に固定する。
2. 3シナリオを1件ずつ、前回の出力と修正履歴を知らない新しい実行担当へ渡す。
3. 各シナリオを、前の出力を知らない実行担当で2回実行し、成果物、読んだ資料、判断のやり直し、迷った点を保存する。判定または新しい曖昧点が一致しなければ、別の実行担当で3回目を行う。
4. 条件を、満たす=1、一部満たす=0.5、満たさない=0で採点する。
5. `[critical]` が一つでも一部満たすまたは満たさないなら、その実行全体を不合格にする。
6. 曖昧点を `Issue / Cause / General Fix Rule` の形で記録し、修正は一般化できる規則だけにする。
7. 修正後は、修正前の出力を知らない新しい実行担当で全シナリオを再評価する。

大幅改修では、可能なら改修前コミットまたはスキルなしの結果も同じ条件で取得する。基準値を取得できなければ、その理由を記録し、推測値で補わない。

## Project専用の重点

- Projectの所有者、番号、node ID、公開範囲、リポジトリとの紐付けを変更前後に確認する。
- Projectフィールド、組織Issue Type、組織Issue Fieldの正本分担をフィールド単位で決める。
- `Effort`、`Estimate Confidence`、依存関係、変更競合、各段階のWIP上限から`Forecast`と実行Waveを組む。
- Milestone期限はIssue/PR側から読み取るだけにし、`Forecast`の入力として扱う。
- Issue/PR側で`Assignee`、linked branch、open PRの整合を確認した着手情報だけをProject側の`Status`へ派生同期する。現在の実行環境が追跡値を提示した場合だけ`Agent Run`へ記録する。
- 着手情報の候補が複数ある、識別子が一致しない、またはGitHubの現在値と矛盾する場合は、Project側で採用候補を決めず同期を停止する。
- レビュー、重いCI、マージ待ちの容量が満杯なら新規投入を停止し、容量解放後に再計算する。
- 権限不足、定義衝突、公開範囲不一致、所有者やアイテム種別の混在、必要な容量情報の欠落では変更前に停止する。
- Issue本文、Milestone、親子・依存関係、Issue Forms、PRテンプレート、CI設定を変更・削除しない。
- Pythonの一括変更スクリプトを使わず、GitHub MCP、`gh`、`jq`による段階別の変更と再取得を示す。

## 収束条件

同じ評価条件で、新しい曖昧点が2回連続0件になった場合だけ収束候補とする。発火評価と出力評価のどちらかに新しい曖昧点があれば修正し、新しい実行担当で連続回数を数え直す。最後に未使用の境界シナリオを追加し、既存区分の期待値を崩さないことを確認する。

## 独立実行の制約

- 自動読み込み率は、外部の`codex exec`など、各回を独立した新規実行として開始でき、`SKILL.md`の読み込み有無を確認できる経路で測る。
- `description`だけを期待値を知らない新しい実行担当が分類する評価は、自動読み込み率ではなく独立発火判定として別に記録する。
- 出力品質は、前の出力と修正履歴を知らない新しい実行担当へ対象スキルと問い合わせだけを渡して測れる。期待条件は出力後に別途採点する。
- 同じ会話の再開、執筆担当による代行、期待値を見せた自己採点は、新しい実行担当の代わりにしない。
- モデル互換性、認証、利用上限、実行枠不足で完了できない場合は、該当回を未実施として理由を記録し、合格数へ含めない。
- 実行時間、道具の使用回数、`SKILL.md`の読み込み有無を取得できない場合は「取得不可」と記録し、推測しない。
- 自動読み込みを測定できなくても、独立発火判定と出力品質の予備採点は記録できる。ただし、自動発火の合格や全評価の収束とは記録しない。

## 記録様式

実行日、対象コミット、実行担当の識別方法、学習用・検証用の区分、3回分の発火有無または採点、`[critical]`の判定、曖昧点、修正内容、取得不可の値を残す。分割前の記録は履歴として保持しても、現行スキルの合否には使わない。
