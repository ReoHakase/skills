# 経験的検証

このスキルを大きく変更した後に、発火条件と出力品質を別々に検証する。執筆者の自己確認だけで合格にしない。

# 評価資産

- `evals/evals.json`: 実際の成果物を評価する3シナリオと、事前に固定した合格条件。
- `evals/trigger-train.json`: 説明文を調整するための発火学習用20問。
- `evals/trigger-validation.json`: 過剰適合を確認するための未使用8問。

発火学習用の失敗だけを説明文の修正に使う。検証用の結果を見てから文面を合わせない。

# 出力品質の検証手順

1. `description` が主張する用途と、SKILL本文・参照資料が実際に扱う範囲を照合する。
2. `evals/evals.json` の各シナリオを、先入観のない新しい実行役へ1件ずつ渡す。
3. 大幅改修では、同じシナリオを改修前のコミットまたはスキルなしでも実行し、基準値を作る。
4. 実行役には成果物に加え、理解・計画・実行・整形のどこで迷ったかを報告させる。
5. 各曖昧点を `Issue / Cause / General Fix Rule` の形で記録する。
6. 事前に固定した合格条件を、満たす・一部満たす・満たさないの3値で採点する。
7. `[critical]` が1件でも一部または不合格なら、そのシナリオ全体を不合格にする。
8. 修正後は前回を知らない新しい実行役で再評価する。

正確性は、満たす=1、一部=0.5、満たさない=0として合計し、条件数で割る。合格後も、不要な参照探索、判断のやり直し、裁量補完が多ければ文面を減らすか、参照先の案内を近づける。

# 発火条件の検証手順

1. 学習用20問を各3回実行し、SKILL.mdが実際に読まれた回数を数える。
2. `should_trigger: true` は発火率50%以上、`false` は50%未満を合格とする。
3. 学習用の誤りを一般化して `description` を1テーマだけ修正する。
4. 学習用が安定した後に検証用8問を各3回実行する。
5. 検証用で精度が落ちた場合は、個別語句を足さず、対象業務と近接業務の境界を書き直す。

特に、次の近接依頼を誤発火させない。

- 単一Issueの閲覧・要約・通常起票。
- 通常のPRコードレビューやレビュー指摘対応。
- GitHub Actionsの失敗修正。
- 一般的なGit・`gh`コマンドの質問。
- 単一Milestoneの作成だけ。

# 検証時の重点項目

- `plan -> apply -> verify` と確認文字列の境界を守る。
- StatusはProjectフィールド固定、Typeは組織Issue Type一式またはProject Type、その他はフィールド単位で正本を選ぶ。
- 権限不足、定義衝突、公開範囲不一致、所有者・アイテム種別混在では停止する。
- Milestone期限を先に決め、末端IssueのEffort、依存関係、変更競合、WIP上限からForecastを組む。
- `ready`、`in-progress`、`in-review`、`blocked`、`done` を作業可能性と型別完了条件で更新する。
- 作業権取得、Agent Run再取得、独立した`worktree`、下流WIPを含めて実行Waveを決める。
- Issue Forms、Issue本文、PR本文へ、選択した正本の値や依存関係を重複させない。
- PRはブランチ作成型Issueを正確に1件だけ閉じ、適用できる確認と未実施理由を示す。
- マージキューの利用資格と設定済み状態を混同せず、未確認なら作業開始前に停止する。
- 日本語では、正式名称・項目名・コマンド・状態値以外の不要な英単語を混ぜない。

# 失敗パターン台帳

- **本文へ構造化メタデータを複製する**
  - 例: Issue本文にPriorityやForecast、依存関係一覧を書く。
  - 一般修正規則: 値の保存先と本文の説明責任を分離し、各情報の正本を一つにする。
- **状態要約から完了を短絡する**
  - 例: PRマージだけで `done` にする、修正可能な失敗を `blocked` にする。
  - 一般修正規則: 状態遷移ごとに操作、確認値、型別完了条件を結び付ける。
- **能力と設定済み状態を混同する**
  - 例: 組織所有の公開リポジトリというだけでマージキュー運用中と報告する。
  - 一般修正規則: 利用資格、現在設定、変更権限を別々に読み、未確認値を推測しない。
- **参照先が広すぎて全資料を読む**
  - 例: 単一のIssue本文作成で初期構築・解除資料まで読む。
  - 一般修正規則: SKILL.mdに判断境界を残し、詳細資料は作業時点ごとに一つずつ案内する。

# 収束条件

同じ評価条件で新しい曖昧点が2回連続0件になり、正確性の改善が3ポイント以下になったら収束候補とする。最後に未使用の境界シナリオを1件追加し、直近平均から15ポイント以上落ちないことを確認する。実行環境が手順数や所要時間を返さない場合は、その値を推測せず「取得不可」と記録する。

- `evals/fixtures/docs/spec.md` を追加し、新規Projectのシナリオへ実際の仕様入力を結び付けた。
- Project番号がまだない作成段階に、リポジトリ、Project所有者、タイトル、公開範囲を含む `OWNER/REPO#create-project:PROJECT_OWNER:PROJECT_TITLE#PRIVATE` 形式の専用確認を追加した。作成後は番号とIDを再取得し、通常の `plan` からやり直す。
- ビューの名前・レイアウト・フィルターを自動検証し、グループ化・並び替え・ボード列・ロードマップ日付フィールドを画面で手動確認する境界を追加した。

## 発火条件

最初の境界確認8問は、期待値を見せず `description` だけで静的分類し、8 / 8件が期待どおりだった。ただし判断理由から説明文を修正したため、この8問は学習用へ移し、検証用としては扱っていない。Project/Milestoneの単発コマンド、単一Issueの通常起票・本文編集、単一PRの本文編集・レビュー対応を除外側へ明記した後、未使用の検証用8問を別に作成した。説明文を固定してから期待値を見せずに静的分類し、こちらも8 / 8件が期待どおりだった。

これは実際にSKILL.mdが読まれた回数ではない。学習用20問と検証用8問を各3回実行する発火率測定は未実施であり、合格とは記録しない。

## 制約と次回条件

- 先入観のない実行役を2件に使用した。3件目は新しい実行枠を確保できず、別シナリオを終えた実行役へ参照を選び直させた。
- 修正後の再評価は同じ実行役を1回中断・再開して完了した。前回を知らない新しい実行役による評価ではなく、新しい曖昧点が2回連続0件という収束条件も満たしていない。
- 改修前コミットまたはスキルなしの基準値は取得していない。
- 実行役の所要時間と道具使用回数は取得不可であり、推測していない。
- 独立したローカル実行は2回試したが、モデル互換性と利用上限で成果物を得られなかったため採点から除外した。

次回は、修正後の3シナリオを新しい実行役で2回評価し、発火学習用20問と検証用8問を各3回実行する。収束後に未使用の境界シナリオを追加する。
