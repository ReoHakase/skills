# Issueの設計と本文

仕様、不具合、運用要求をIssueへ分けるとき、またはIssue本文とIssue Formsを作るときに読む。

# 分割手順

1. 達成したい成果と非スコープを確認する。
2. 大きな成果は`epic`にし、1つのPRで閉じられる末端Issueへ分ける。
3. 複数実装が共有する契約や境界を先にIssueへ切る。
4. 親子関係と実行順序を分けて考える。
5. stacked PRを使う場合も、成果の階層、着手を止める依存、branchのbase順を分けて考える。
6. 変更予定ファイルを比較し、論理的な依存がない変更競合はblocked byにしない。
7. 受け入れ条件と確認手順を第三者が判定できる形にする。

独自のWBS番号は使わない。GitHub Issue番号、sub-issue、blocked by / blockingを使う。

テスト、ドキュメント、可観測性は、対象実装と同じPRで完了できるなら末端Issueの受け入れ条件へ含める。単独でマージする価値と独立した完了条件がある場合だけ別Issueへ分ける。

# Issue粒度

ブランチ作成型Issueは次を満たす。

- 1つのPRで閉じられる。
- 主な変更境界が1つである。
- 受け入れ条件を第三者が確認できる。
- 非スコープが明確である。
- 変更予定ファイルをglobで示せる。
- 必要な確認手順がある。
- Issue本文だけで作業開始の可否を判断できる。

分割を再検討する兆候:

- UI、API、DB、基盤、文書を同時に広く変更する。
- 複数の未確定な設計判断が残る。
- 複数人や複数エージェントが並列化できる作業を押し込んでいる。
- 巻き戻し、展開、レビューの境界が複数ある。
- 受け入れ条件や変更予定ファイルが多く、1回のレビューで把握しにくい。

数だけで機械的に分割しない。分割後のIssueがそれぞれ利用可能な成果を持たず、常に同時マージが必要なら分割しすぎである。

# stacked PR向けの分割

stacked PRを使う場合も、成果の階層は`epic`とsub-issueで表す。Stackはbranch、レビュー、マージの直列順序であり、成果の親子関係ではない。詳しい運用は`stacked-prs.md`を参照する。

- すべてのStackを1つの`epic`に所属させる。
- Stackの1段を、1つの末端Issue、1つのbranch、1つのPRに対応させる。
- 各PRは対応する末端Issueだけを閉じ、`epic`を閉じない。
- 1つの`epic`に複数のStackや通常PRを含めてよい。ただし、1つのStackを複数の`epic`へまたがせない。
- 上段PRを下段PRのマージ前に実装、確認、レビューできるなら、Stackの隣接関係をblocked byへ変換しない。
- 独立して並行できる変更は同じStackへ押し込まず、通常PRまたは別のStackにする。

既存Issueを分割し直す場合は、現在の進行状態を先に確認する。linked branchもPRもなければ、元Issueを`epic`へ再整理し、実装を末端Issueへ分けてよい。branchまたはPRがすでにある場合は新しい`epic`を作り、元Issueを既存branchとPRに対応する末端Issueとして残す。既存作業を`epic`へ付け替えたり、同じPRで`epic`を閉じたりしない。

# Issue本文の正本

Issue本文には、現在信頼できる作業契約だけを書く。状態変化、判断の履歴、阻害要因、引き継ぎはコメントへ書く。

Issue本文へ書かないもの:

- sub-issue一覧、blocked by / blocking一覧
- Milestone、Assignee、linked branch、PR
- Projectフィールドや組織Issue Fieldの値
- 認証情報、個人情報、公開できないログ
- 未確定な実装メモやチャットの全文

同一リポジトリのIssue、PR、コミットは`#123`または短いSHAで参照する。別リポジトリは`OWNER/REPO#123`と書く。

# 種類ごとの必須内容

| 種類               | 必須内容                                                                              |
| ------------------ | ------------------------------------------------------------------------------------- |
| 機能追加・通常作業 | 概要、背景、非スコープ、変更ファイル、参照ドキュメント、受け入れ条件、確認手順        |
| 不具合             | 通常作業の内容に加え、期待動作、実際の動作、再現手順、ログ・証拠、影響範囲            |
| 調査               | 背景、問い、時間枠、停止条件、判断基準、成果物と証拠、後続Issue、非スコープ、確認手順 |
| 大項目             | 目的、成果の境界、完了条件、状態集約の根拠                                            |
| リポジトリ差分なし | 通常作業と同じ。変更ファイルに「なし」と理由を書く                                    |

規範となる資料がある場合、`参照ドキュメント`はコミットSHAと行番号に固定する。根拠資料が存在しない場合は、理由付きで「なし」と書き、可変なbranch URLを代わりに置かない。

```text
https://github.com/OWNER/REPO/blob/<commit_sha>/docs/spec.md#L10-L40
```

更新確認には比較URLを添える。

```text
https://github.com/OWNER/REPO/compare/<commit_sha>...<default-branch>
```

# 通常作業の本文例

```markdown
# 概要

このIssueで実現することを書く。

# 背景

なぜ必要かを書く。

# 非スコープ

- このIssueでは扱わないことを書く。

# 変更ファイル

- `src/**/*.ts`
- `tests/**/*.test.ts`

# 参照ドキュメント

https://github.com/OWNER/REPO/blob/<commit_sha>/docs/spec.md#L10-L40

更新確認: https://github.com/OWNER/REPO/compare/<commit_sha>...<default-branch>

# 受け入れ条件

- [ ] 第三者が確認できる条件を書く。

# 確認手順

- [ ] 実行するテストまたは手動確認を書く。
```

# 不具合本文の追加項目

```markdown
# 期待動作

正しい動作を書く。

# 実際の動作

観測した動作を書く。

# 再現手順

1. 再現操作を書く。

# 環境

- OS、ブラウザ、実行環境、コミットなど必要な情報を書く。

# ログ・証拠

秘密情報を除いた最小限の証拠を書く。

# 影響範囲

利用者、機能、データ、頻度への影響を書く。
```

# 調査Issue

調査は時間枠を持ち、結論が出ない場合も証拠と残った不確実性を成果物にする。終了時に本文を更新し、採用案、棄却案、理由、後続Issueの要否を確定する。

# 起票と更新

本文を一時ファイルへ作り、内容を確認してから起票する。

```bash
gh issue create \
  --repo OWNER/REPO \
  --title "自然な言葉のIssueタイトル" \
  --body-file issue.md
```

既存Issueの契約が変わった場合は、PRをレビュー可能にする前に本文を更新する。

```bash
gh issue edit ISSUE_NUMBER \
  --repo OWNER/REPO \
  --body-file issue.md
```

Issue Formsを導入するときは`assets/.github/ISSUE_TEMPLATE/`を対象リポジトリへコピーし、既存テンプレートと重複しないか確認する。
