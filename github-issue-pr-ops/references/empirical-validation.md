# 経験的検証

このスキルを大きく変更した後は、発火条件と出力品質を分けて検証する。執筆者の自己確認を実行結果の代わりにしない。

# 評価資産

- `evals/trigger-train.json`: 説明文を調整するための学習用20問。
- `evals/trigger-validation.json`: 過剰適合を検出するための未使用8問。
- `evals/evals.json`: ProjectなしでのIssue分割、着手競合と引き継ぎ、PR契約を評価する3場面。
- `evals/fixtures/docs/spec.md`: 仕様からIssueへ分割する場面の固定入力。

発火評価の問い合わせ集合は`github-project-ops`と同一にする。期待値だけを各スキルの責務に合わせ、Issue/PRのみと両方の依頼をこのスキルの発火対象にする。学習用の失敗だけを説明文の修正へ使い、検証用の結果を見て文面を合わせない。

# 発火条件の検証

1. 説明文と本文の責務が一致していることを静的に確認する。
2. 学習用20問を、前の判断を知らない新しい実行担当で各3回実行する。
3. 各回で`SKILL.md`が実際に読まれたかを記録する。回答内容から発火を推測しない。
4. `should_trigger: true`は発火率50%以上、`false`は50%未満を合格とする。
5. 学習用の誤りだけから一般化した境界を1テーマずつ修正する。
6. 説明文を固定した後、検証用8問を新しい実行担当で各3回実行する。
7. 検証用で悪化した場合は個別の語句を足さず、対象業務と近接業務の境界を見直す。

4区分を別々に集計する。

- Issue/PRのみ: このスキルだけが発火する。
- Projectのみ: `github-project-ops`だけが発火する。
- 両方: 2つのスキルが発火する。
- 不要: どちらも発火しない。

特に、Issue要約、担当者変更だけ、通常のコードレビュー、CI失敗修正、翻訳、一般的なGit操作、単発の`gh`コマンドでは発火させない。

# 出力品質の検証

1. `evals/evals.json`の3場面を、前の実行や期待値を知らない新しい実行担当へ1件ずつ渡す。
2. 各場面を、前の出力を知らない実行担当で2回実行する。判定または新しい曖昧点が一致しなければ、別の実行担当で3回目を行う。大幅改修では、可能なら同じ入力を改修前版またはスキルなしでも実行する。
3. 実行前に固定した各条件を、満たす、一部満たす、満たさないの3値で採点する。
4. `[critical]`が1件でも一部または不合格なら、その実行全体を不合格にする。
5. 満たす=1、一部=0.5、満たさない=0として条件数で割り、正確性を算出する。
6. 各判定には成果物の該当箇所を根拠として付ける。
7. 実行担当には、理解、計画、実行、整形のどこで迷ったかと、判断をやり直した回数を報告させる。
8. 曖昧点は`Issue / Cause / General Fix Rule`の形で記録し、同じ原因を失敗パターン台帳へまとめる。

修正するときは、どの条件の判定文を満たすための変更かを先に記録する。一度に直すのは1つの原因群に限り、修正後は前回を知らない新しい実行担当で全場面を再評価する。

# 収束

次の条件を2回連続で満たすまで収束としない。

- 重大条件の不合格が0件。
- 新しい曖昧点が0件。
- 前回からの正確性改善が3ポイント以下。

道具使用回数と所要時間を取得できる場合は、それぞれの変動が10%以内、15%以内かも補助指標として記録する。取得できない場合は「取得不可」とし、推測値で収束を判定しない。

発火条件は、収束候補になった後に学習用にも検証用にも使っていない境界問い合わせを1件追加する。出力品質は責務や不変条件を変えた場合に未使用場面を追加し、直近平均から正確性が15ポイント以上落ちた場合は、評価場面の分け方から見直す。

# 実行環境の制約

- 同じ実行担当を再利用できない環境では、別の実行環境または別セッションを使う。
- 新しい実行担当を用意できない場合は、経験的評価を省略したと明記し、自己再読を代替結果にしない。
- `SKILL.md`を読んだ事実を取得できない環境では、発火率を推測せず未測定とする。
- `description`だけを新しい実行担当が分類する評価は、独立発火判定として自動読み込み率と分けて記録する。
- 道具使用回数、所要時間、トークン数を取得できない場合は、値を推測せず取得不可と記録する。
- GitHubへの書き込み権限や検証用リポジトリがない場合は、計画成果物の評価と実変更の評価を分ける。

結果は実行ごとに保存し、3回分を区別する。数値が未取得の段階では、静的分類だけを合格結果として記録しない。
